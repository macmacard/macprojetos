O elo entre os dois lados é a pasta /Repos/cardosoamelia2001@gmail.com/macprojetos — uma cópia do repo github.com/macmaccard/macprojetos (branch master) que vive dentro do workspace.

Fase 1 · uma vez por repositório

Puxar o repo para o Databricks

  1. Vincular a credencial do GitHub — em Configurações › Contas vinculadas (Linked Accounts). O Databricks passa a autenticar como você nas operações Git, sem senha em nenhum notebook.
  2. Clonar o repositório — em Repos › Add Repo › Clone, informando a URL github.com/macmaccard/macprojetos. O Databricks cria a pasta /Repos/<seu-email>/macprojetos já sincronizada com o remote.
  3. Selecionar a branch — master, a linha principal de histórico.

No nosso caso: o repositório já existia no GitHub desde 2018 (commit "Initial commit"), e em 08/11/2026 o notebook do Desafio 1 (CredAIR) entrou nele. Depois disso, sempre que o remote muda, basta um pull (Menu Git › Pull) para atualizar a cópia local.

Fase 2 · trabalho do dia a dia

Alterar dentro do Databricks

  • O notebook fica dentro da pasta do repo (desafios/analise-credito/) e é editado/executado como qualquer outro;
  • Nada vai para o GitHub sozinho. Cada alteração fica na área local (working tree) marcada como M (modificada) ou ?? (arquivo novo, não versionado);
  • Nesta história: ao final da análise, geramos dois arquivos novos na pasta — o HTML e o .ipynb com os resultados completos da execução;
  • Antes de publicar, sempre revisar: status (em que branch estou? o que mudou?) e diff (o conteúdo exato de cada mudança).
?? desafios/analise-credito/Desafio 1 - Análise de Crédito (com resultados).html
?? desafios/analise-credito/Desafio 1 - Análise de Crédito (com resultados).ipynb
Fase 3 · gravar e enviar

Publicar a nova versão

  1. Escolher os arquivos do commit (pode ser tudo, ou só alguns);
  2. Escrever uma mensagem descritiva — o que entrou e por quê;
  3. Commit + push para a master — o GitHub recebe a nova versão na hora;
  4. Verificar: o status volta limpo (isClean: true), sinal de que tudo foi publicado.

Fechando o ciclo

Boas práticas do fluxo

  • Pull antes de começar — evita trabalhar sobre versão desatualizada e conflitos;
  • Commits pequenos e frequentes — cada commit conta uma história coerente (um arquivo/assunto por vez, como fizemos: HTML e .ipynb separados);
  • Mensagens que explicam o "o quê" e o "porquê" — o histórico do repo é a documentação do projeto;
  • Revisar antes de publicar — status + diff levam segundos e evitam publicar arquivo errado;
  • Trabalhos grandes vão em branch — crie uma branch, publique lá e integre à master quando estiver pronto.

Git ↔ Databricks: clone = Add Repo · pull = menu Git › Pull · status/diff = painel Git · commit+push = Commit com push marcado.
